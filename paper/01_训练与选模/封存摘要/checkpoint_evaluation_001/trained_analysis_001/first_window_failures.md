# 首窗口两次失败：物料流水只读诊断

两个失败班的首窗**已卸入破碎FIFO的全部矿料组成均合规**，但部分较高品位物料在窗口末尾仍留在FIFO，实际已处理部分的品位低于0.26。两班在末段之前均曾合规，随后FIFO处理了大量低品位头料，且临界时刻剩余处理能力不足以消耗后面的较高品位料。这里识别的是实际物料账务与结算时序，尚不能把失败归因于某一个网络模块或Reward权重。

读取范围：本轮100班首窗物料journal及正式per_window.csv；仅对9950012、9950029读取完整原始动作和观测。未加载模型、未重新推理动作、未训练、未生成新班次。所有journal按独立完成审计中已封存SHA核对；两班原始HDF5由正式只读reader核验。

## 100班参照

首窗98/100合规；品位均值 0.269871739，中位数 0.269632484，P5/P95=0.264475590/0.275907382。两失败班是最低的第1、第2名。首窗处理吨位均值 4022.393t；期末FIFO存量均值 251.962t。

这里将单批物料G<0.26记为低品位、0.26≤G≤0.28记为带内、G>0.28记为高品位；这是原矿批次分箱，窗口目标仍是混合处理品位。观测到的供料源依次为Load0约0.38、Load1约0.30、Load2约0.15；Load1相对Load0是较低的高品位源。Load3为废石，不进入这份破碎矿石journal，0吨不能解释为没有废石生产。

最后快照分别在7071.12s和7094.23s，是该次动作前的原始观测，不是7200s的完整盘点；已载包含行驶、排队或服务阶段，不能全部称为道路在途。两班最后动作均为Load3（废石），但剩余不到130秒；从首窗已完成运输的动作→UNLOAD实测最短约983s/1005s，不能将最后一拍动作直接认定为本窗失败的主因，也不能把这些实测最短值当所有替代动作的硬下界。

JSON逐条保留原动作、候选可预留吨数、已载矿石grade、当前装载预留、FIFO及动作→UNLOAD来源匹配。两个班的全部首窗UNLOAD均与此前同车最新动作匹配成功；同一秒使用journal seq排序，避免把卸载后的新动作配到上一批料。累积派车吨数是流量，未与FIFO/已载/剩余预留相加，以免重复计数。

## 能支持与不能支持的解释

流水支持：本轮两例都发生了“早先窗口平均已合规→末段处理低品位头料→较高品位已到货却未在边界前处理”的路径；已到货总组成可达到业务合规，但可被本窗结算的子集不足。9950012还伴随偏高的全窗低品位处理占比，9950029则更突出Load0/Load1的替代比例和末段集中性。

下一步值得核查的是现有C128、FIFO业务边和候选评分是否利用了窗口剩余时间、FIFO头部顺序、待处理高低品位数量及到达时间；本报告没有检验模型是否实际利用这些通道。仅凭这两例，不能决定应增加GAT层数、改Reward权重或追加模型分支。

缺失与限制：无LOAD_COMPLETE事件，无法精确恢复装载完成时刻；未有边界7200s车辆全量快照，无法精确盘点那一刻所有在途/预留；原始快照中已载车辆的来源Load不总是显式保留，不使用未来UNLOAD反填。中间任意整点的聚合PROCESS只有可见时间前缀，不能做没有依据的线性插值。两例属于描述性失败诊断，不能替代对干预策略的实测。

可复核材料：`first_window_failures.json`包含100班首窗分布、两失败班完整分项与来源SHA；脚本位于对应change_plans目录的 `trained_analysis_001/analyze_first_window_failures.py`。
