# DISPATCH-inspired V2 的破碎 FIFO 审查

本次审查使用封存的 V2 源码、历史标称班的观测与物料事件，以及独立构造的反例。正式 500 班继续使用原冻结方案，研究结论引用对应版本。

## 物理结算

AnyLogic 的矿车先获取卸载位，再按仓容等待队首申请整车预约。入卸载服务前须满足仓内矿量 (B) 加已预约吨位 (Q) 再加本车载重 (q) 不超过 500 吨。完成卸载后，物料从预约转到 FIFO 队尾。破碎机按每小时 2,500 吨从队头消耗，在 7,200 秒的窗边界切分。归窗按实际破碎吨位和金属量，空窗单独计分。历史 `run_10004025` 的 `batch-28` 共 91.7 吨，其中 90.407246 吨在第一窗破碎，余下 1.292754 吨在第二窗破碎。 [仓容队首处理](../../../../../anylogic/3d/DRL-PPO-baseline1/DRL-PPO-baseline1.alp#L20218) · [卸载与 FIFO 入队](../../../../../anylogic/3d/DRL-PPO-baseline1/DRL-PPO-baseline1.alp#L19952) · [跨窗破碎](../../../../../anylogic/3d/DRL-PPO-baseline1/DRL-PPO-baseline1.alp#L20048)

上层的既有承诺重放以已知 FIFO 库存、正在服务与在途车辆作为起点，输出逐窗吨位和金属量。该结果只加一次。下层台账也只在 RPC 回显确认后累计实际派车吨位。 [既有承诺重放](../../../../../traditional_dispatch_v2/flow_plan.py#L81) · [承诺与新增计划合并](../../../../../traditional_dispatch_v2/flow_plan.py#L308) · [回显确认](../../../../../traditional_dispatch_v2/runtime.py#L145)

## 两层决策与物理 FIFO 的差异

| 对象 | 可复现现象 | 影响 |
| --- | --- | --- |
| 新吨流归窗 | 对整段均匀发车只使用最早一次预计入仓时的已承诺积压。简化窗长 100 秒、速率 1 吨／秒，既有 80 吨在第 20 秒入仓，新车卸载延迟 10 秒、每车 10 吨。代码预测本窗兑现 85%，逐派车时刻插入同一已知 FIFO 只兑现 10%。 | 上层错误分配同一装点矿料到各窗口。方向取决于积压随时间增减。 [固定偏移](../../../../../traditional_dispatch_v2/flow_plan.py#L217) |
| 计划物理可行性 | 对历史 `run_10004025` 的首帧按求解器自身的分布和时间偏移还原，最优解的窗内处理峰值为 2,653.277 吨／小时。对同一班第 8 帧还原入卸载服务与破碎累计量，在 1,633 秒时预测仓内加预约为 558.628 吨。 | 整窗总量约束容许瞬时超速、超仓容。HiGHS 的最优解只证明聚合 LP 可解。 [整窗约束](../../../../../traditional_dispatch_v2/flow_plan.py#L314) |
| 下层实时匹配 | 计算预测到铲排队、相对空驶和装点首个待满足吨位的派车时差。只余 1 吨目标需求的站，若恰逢首吨到期，派 100 吨车的目标偏差仍为零。车型流量在此处聚合为装点总目标。 | 下层的目标吨流追踪允许超额派吨，且缺少卸载位、仓容准入和破碎 FIFO 的候选效应。 [装点目标](../../../../../traditional_dispatch_v2/dispatch_policy.py#L117) · [匹配损失](../../../../../traditional_dispatch_v2/dispatch_policy.py#L144) |

两个历史快照的超限来自对 LP 自身流体时间分布的还原。实跑按 AnyLogic 的队列和仓容限制执行。

## 可以单独修复的实现问题

| 检查项 | 反例 | 修复方式 |
| --- | --- | --- |
| 发布向量可行性 | 注入一个接近容差的 `feasible_limit` 解，验证时最大行残差约 0.001 吨。非负截断后，首个装点供给约束超出 0.0025 吨，仍发布。 | 对实际发布的截断向量重新验证全部约束。 [解验收](../../../../../traditional_dispatch_v2/flow_plan.py#L370) |
| 余料解码 | 147 吨库存和首车载量分别按 float32 编码，匹配保留约 (5.26\times10^{-6}) 吨残量，并为虚拟第二车计算一斗服务。 | 对库存、载量的独立量化误差做保守判定，真实部分载荷继续通过。 [匹配预留](../../../../../traditional_dispatch_v2/dispatch_policy.py#L177) |
| 分段逆函数 | 首段 100 吨，已派 99.9999995 吨。把尚未用完的一段当作耗尽后，负余量使后一段需求时刻跑到 3,927.273 秒，早于该段 7,200 秒起点。 | 先确定哪一段仍有目标，再对该段有效累计量求逆，防止跨段引入负余量。 [需求逆函数](../../../../../traditional_dispatch_v2/dispatch_policy.py#L133) |
| 同时到铲 | 在途 8 号车和拟派 0 号车同刻到站。下层日历用在途身份优先，共享名义堆按车号排序。构造的两个候选在两种规则下选站反转。 | 在共享预测器中统一并明确同刻规则。AnyLogic 的同刻顺序由实际事件到达记录核验。 [铲位日历](../../../../../traditional_dispatch_v2/dispatch_policy.py#L90) · [名义事件堆](../../../../../traditional_dispatch_v1/nominal.py#L496) |

## 将 FIFO 接入下一版

保留上层 LP 生成按装点和车型的目标吨流。对下层每个候选小匹配，用共享的离散事件预测器插入新增车次并重放同一份已承诺计划。轨迹包含到铲、装车、到卸点、等待卸载位、仓容队首、整车预约、卸完入队和跨窗破碎。各候选重算达到期限时的窗口矿吨与金属吨，同时统计新增卸载排队和仓容等待。原吨流偏差至少按整车未覆盖额度计算。目标权重和观察时域须在新验证前冻结。

验收应覆盖满仓且只有队首可入、先到低品位或高品位引起的换窗、同刻卸载、整车预约、部分载荷、班末到达和真实低矿量窗。现场对比须使用同条件的旧 V2 与新实现，并通过留存的精简回执比较预测与实际。当前已完成的 60 槽里，DISPATCH 末窗有 49 班超 28%，但正式班的低频记录不足以给出具体批次的归因。

## 前 60 槽的匹配回放

60 个 DISPATCH 班的首个实时匹配都对应决策 0、模拟时刻 0、当前车 3。60 份回执的原始观测 SHA256 相同，与封存班 `10004025` 的首帧逐字节一致。用该帧核对全部回执、班次身份与 Java START，独立复算 4 个单车候选和 64 个三车组合。三车顺序为 3、0、1。V2 最小匹配损失为 103.100434，字典序取装点组合 `(0,0,2)`，首车发往装点 0。动作、三车规模和 68 次评分与 60 份回执一致。后两辆只是匹配中的预测车辆。

对同一批 64 个组合，先依组合派出三辆车，再通过共享名义模型计算仓容、FIFO 和破碎。仅兑现三车时，V2 首选对应首窗 330.400 吨、品位 31.6165%。组合 `(2,0,0)` 在相同矿量下对应 27.7669%，其匹配损失为 118.242628。将三车之后的续派规则固定为相同的名义贪心规则，V2 组合的整班预测成本为 7.138211，按 FIFO 联合成本在 64 个组合中排序，`(2,0,2)` 成本最低，为 0.249242。这些数值是共享首帧上的反事实预测。

60 班共记 11,303 次实时多车匹配。记录只保留每班的首个匹配见证和其他匹配的计数，后续 11,243 次缺少逐请求原始输入和动作。现有证据支持复算 60 个首个见证，直接输入仅有一个不同的快照。
